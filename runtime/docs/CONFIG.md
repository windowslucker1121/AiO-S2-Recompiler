# Configuration reference

Settings come from an ini file and from environment variables. The lookup order for a key is: environment variable, then ini value, then the default in the code. The runtime loads `nxrt.ini` from the working directory unless `NXRT_INI` or `InitOptions.ini_path` names another file; a missing file is not an error. Each key read is logged at Info level under the tag `config` with its value and its source (`env`, `ini` or `default`).

Rules:

- Section and key names are case-insensitive.
- Ini syntax: `[section]` lines, then `key = value`. A `;` or `#` that follows whitespace starts a comment. A quoted value is taken verbatim.
- The environment variable for a key is `NXRT_` plus the upper-case section, an underscore, and the upper-case key, with every non-alphanumeric character replaced by `_`. Example: `[diag] watchdog_seconds` is `NXRT_DIAG_WATCHDOG_SECONDS`.
- Integers accept decimal and `0x` hex. Booleans accept `1`/`0`, `true`/`false`, `yes`/`no`, `on`/`off`. Doubles must parse completely. Text that does not parse keeps the default.

### Audio notes

When the sink has a clock of its own (XAudio2, or `paced`), the audio renderer keeps about 40 ms of audio queued on it and renders the next 5 ms frame whenever the queue falls below that, instead of waiting on the host clock. The sound card and the host clock never agree exactly; pacing by the host clock alone would fill the queue slowly (frames dropped) or drain it (a click). With the null sink the renderer keeps its 5 ms host-clock pacing. The pace does not depend on the game's frame rate: the renderer runs on its own thread and the game's audio thread waits for the renderer's frame event.

`wav_dump` is read when the first audio sink is created and works with either sink. `device` and `volume` only affect the XAudio2 sink (the null sink plays nothing). `device` is read each time the XAudio2 sink opens. `volume` is read once, at first use, and can also be changed in code while the program runs.

`wav_dump` writes the game's sound to a WAV file as well as to the output device. Every frame that reaches the sink is written, including frames the device drops because its queue is full. The file header is updated about once a second of audio and again when the sink closes, so a file from a run that was killed is still playable up to the last update. If the sample rate or channel count changes during the run (for example a switch from stereo to 5.1), the next file gets a number before its extension: `dump.wav`, then `dump.1.wav`, and so on.

`device` chooses where the XAudio2 sink plays. `default` (or an empty value) uses the system's default output. Any other text is looked for first as an exact endpoint id, then as part of a device's friendly name, ignoring upper and lower case. The first match wins. If nothing matches, the log gets a warning and the default device is used. Each time the XAudio2 sink opens, the log lists the active output devices with their names and ids, so the text for this key can be copied from there.

While a sink is active, a line `sink <name>: queue avg A ms (min..max ms), underruns +N (total), dropped +D, written F frames/s (rate R)` is logged every `stats_interval` seconds. The queue is the audio waiting in the device, which is the output latency; `written` should match the rate (lower: the game is starved or the stream is stretched). When a sink closes, it writes one line to the log with its counters: frames written, accepted, dropped, underruns (times the device ran out of audio after playback had started) and the largest number of buffers queued at once.

## Keyboard and mouse bindings (`controls.ini`)

These live in the play-mode file `controls.ini` (key `[play] controls`), not in `nxrt.ini`. The F1 settings page, the game window's menu
bar and the library write the same file.

Actions: `move_*`, `look_*`, the console buttons `btn_a` ... `btn_rstick`, the d-pad `dpad_*`, `confirm`, `back`, and slots a game module
names itself (`play_types.h` `GameVocabulary`): a primary and a secondary action, targeting, jump, an alternate control scheme, a look
button, map, pause, two sets of four selects (set A, which the mouse wheel cycles with the set's next / previous actions, and set B).
Without a game's own names the slots are called `primary`, `target`, `secondary`, `jump`, `alt_form`, `look_hold`, `map`, `pause`,
`set_a_1` ... `set_a_4`, `set_a_next`, `set_a_prev`, `set_b_1` ... `set_b_4`. Contexts: `all` (a layer under every context) and, by
their generic names, `play`, `alt`, `map`, `menu`, `inspect`; a game may name them too.

How it works: the game only knows the console pad, so an action is turned into pad buttons by the `[console]` table (`[switch]` in older
files, still read). A set select is a short pulse of its output; the wheel skips members the game says the player does not have yet
(`GamePlay::frame` cycle hint). `[mouse] wheel_cycles = 0` (or the game's own name for it) turns the wheel cycling off.

To change a key, add a line `Key = action` to `[bindings.all]` (every context) or to one context (`[bindings.play]`, `[bindings.menu]`,
`[bindings.map]` ...). `Key = none` switches an input off in that context. Key names are SDL scancode names (`Left Ctrl`, `Page Up`,
`Mouse1`, `WheelUp`). A trigger may follow the action: `Space = jump toggle`, `Left Ctrl = alt_form hold 250`.

`[meta] defaults_rev` records the revision of the factory bindings that the file was written with. The game writes it. A file without the section counts as `0`. When a release adds a new factory binding, the game adds it to an existing `controls.ini` at the next start, but only where that key is still unbound in that context. A key you bound yourself is left alone. A file written before `[meta]` existed has no record of what you removed, so a key you had unbound there gets its new default once. After that, a key you remove stays removed. The first time this happens, the old file is kept next to it as `controls.ini.bak` (an existing `.bak` is never overwritten), and the upgraded file is written at once. The log has one line saying what was added. A file with no `[bindings.*]` section gets the whole factory set and is not rewritten. A revision can also change a factory value (`GameDefaultChange`). A file that still has the old factory value takes the new one at the same upgrade; any other value stays.

`[mouse] menu_cursor`, default `1`: in menus the mouse works like a pointer: a visible cursor, hovering highlights an item, left click activates, right click goes back, the wheel scrolls. While it is on, the left click drives no binding in the menu and map contexts. The old key `menu_touch` is ignored; a file that still has it loads without a warning and nothing changes.

Sections of older files that no game uses any more (`[aim]`, `[camera]`) and `[tweaks]` keys the play code does not own are skipped
without a warning; the game's in-place saves leave them in the file.

### Start-up and menus (`controls.ini`, `[tweaks]`)

All off by default; with them off the game starts and plays as it always did. They take effect only for a game module that implements them
(`play_fastboot.h`; none in this repository does yet).

`[tweaks] skip_intro`, default `0`. `1` skips the opening cutscene of a new game without a key press, through the game's own cutscene skip.
Other cutscenes play as usual. Takes effect at the next new game.

`[tweaks] skip_boot_logos`, default `0`. `1` ends the title's intro movie as soon as it starts, so the title screen comes up at once.

`[tweaks] language`, default `auto`. The game's language: `auto` uses the Windows display language when the game has it, else English; a name such as `French` or `LatinAmericanSpanish` picks one (names as in `[system] language`). The library's Extras tab sets it. `[system] language` in the game ini wins over it. Applies at the next start.

`[tweaks] fast_menus`, default `0`, and `[tweaks] menu_speed`, default `2`, range `1` to `4`. With `fast_menus = 1` the front end runs its clock `menu_speed` times faster: its animations, fades and waits. `menu_speed` is read only while `fast_menus` is on. Applies at once.

### Controller sticks (`controls.ini`, `[pad]`)

`[pad] deadzone`, default `0.10`, range `0` to `0.5`: the dead zone of the left stick (movement). Before the right stick got its own key, this was the only stick dead zone.

`[pad] right_deadzone`, default `0.10`, range `0` to `0.5`: the dead zone of the right stick (looking). A file with `deadzone` but no `right_deadzone` gives the right stick the value of `deadzone` when read. The next save writes both keys.

`[pad] invert_y`, default `0`: flips the right stick's vertical axis in play, so pushing up looks down. Menus and the map keep the stick as it is. It adds to the game's own invert option in its controls menu, so with both on, looking is back to normal.

`[pad] look_sens`, default `1`, range `0.25` to `3`: multiplies the right stick's deflection in play. Below 1, the top turn speed is lower. Above 1, it is reached sooner. Like `invert_y`, it applies in play only.

`[pad] alt_orbit`, default `2`, range `0` to `6`: for a game with an alternate control scheme seen from outside (a vehicle, a second form): how fast, in radians per second, the right stick turns its camera at full deflection. `0` turns the stick off and leaves the mouse on.

`[mouse] alt_camera`, default `1`, and `[mouse] alt_sensitivity`, default `2`, range `0.1` to `20`: the mouse turns that camera, at this speed on the Source engine scale of the settings page (2 is the same speed as the default aim, both directions; `alt_yaw` / `alt_pitch` in radians per count set one direction each). A game may give these keys its own names (`GameVocabulary`).

## Window modes and the picture (`controls.ini`, `[display]`)

`window_mode` is `windowed`, `borderless` or `exclusive`. Borderless covers the display at its desktop mode. Exclusive asks Windows for the desktop mode. If the display refuses (a remote or locked session, some drivers), the game logs "window mode 'exclusive' was refused" and uses borderless instead. The setting in the file stays as it was. Alt+Enter and the F1 page switch modes while playing.

The game's picture size (internal resolution) is fixed when the game starts. It is the size of the window or screen at that moment, unless `render_width` and `render_height`, or `render_scale`, are set. Start in `borderless` on a 4K screen and the game renders at 3840x2160. Start windowed and press Alt+Enter, and the picture keeps the window's size and is scaled up, with bars when `keep_aspect = 1`. For a sharp full-screen picture, set the window mode before starting (the library does this), or set `render_width` and `render_height`.

`aspect`, default `auto`: the shape of the 3D view and the HUD. `auto` takes the window's shape at start (or the shape of `render_width` x `render_height` when both are set); `16:9`, `21:9`, `32:9`, `16:10` (any `W:H`) or a number from 1.0 to 5.0 forces one. Title A: on any shape but 16:9 the game's targets get that shape (1080 high when wider, 1920 wide when narrower, then `render_scale` on top), the 3D view is Hor+ (the game's vertical FOV, a wider horizontal one; narrower shapes keep the 16:9 width and show more above and below) and the menus and HUD stay 16:9, centred. `aspect = 16:9` keeps the 16:9 picture with bars. The log line `title A: aspect ...` gives the size used, and the first widened camera logs its vertical and horizontal FOV.

`quality_preset` (`console`, `high`, `ultra`, `custom`; the older `switch2` is read as `console`) and `view_distance` (1.0 to 4.0), live, shown on the F1 Graphics page for games with quality hooks (none ship now). Picking a preset sets `view_distance`, `lod_bias` and `anisotropy` together (Console: x1, 0, game; High: x1.5, -0.5, 8; Ultra: x2, -1.0, 16); changing one of them afterwards makes it `custom`.

On a picture narrower than 16:9 (16:10, 3:2, 4:3), the HUD and the menus keep their full 16:9 width and show more above and below. Wider pictures keep the HUD at 16:9 in the middle, as before.

The frame rate counter (`[fps] corner`) defaults to `top_left`. The bottom corners overlap the menu prompts and the title screen's copyright line.

New self-test steps (`NXRT_PLAY_SELFTEST`, see `play_selftest.h`). `gate:NAME` holds the script until the file `selftest_NAME` exists in the working folder. The file is then deleted and the script goes on. `report[:label]` logs the window mode, pixel size, focus and frame count.

## Named instances

`--instance NAME [--instance-dir DIR]` (or `NXRT_INSTANCE` / `NXRT_INSTANCE_DIR`) runs the game as a named instance beside other runs. The
instance folder is `DIR`, by default `<game folder>\instances\NAME`. Without an instance only one run per game folder may start; with one, only
one run per instance folder. The window title ends in ` [NAME]`. The code is `runtime/src/core/instance.cpp` (`nxrt/instance.h`).

What an instance changes, right after the configuration is loaded. A key set to an absolute path keeps it. A key set to a relative path moves into
the instance folder. The keys below without a default stay off.

| What | Default run | Instance |
|---|---|---|
| Log (`--log`) | `<game folder>\oot.log` | `<instance folder>\oot.log` |
| Crash, freeze, fatal reports, memory-guard report | `<exe>_crash.txt` / `_freeze.txt` / `_fatal.txt` next to the exe | `<instance folder>\<exe stem>_crash.txt` ... |
| `dump_threads` request file | next to the exe | `<instance folder>\dump_threads` (also `dump_threads.<pid>`) |
| `[fs] save_dir` (saves, temporary storage) | `%APPDATA%\<save folder>\save` | `<instance folder>\save` (empty at first; copy a save in to start from it) |
| `[play] controls` | `controls.ini` (game folder) | its own copy, made from the game folder's the first time |
| `[nvn] pipeline_keys`, `[nvn] shader_order` | game folder | own copies, made from the game folder's the first time |
| `[nvn] pipeline_cache` | `pipeline_cache.bin` beside the shader cache folder | `<instance folder>\pipeline_cache.bin`: a hard link to the shared file (a copy across volumes), renewed when the shared one is newer; a private file left from an older run is replaced by the link. The instance only reads it: it never writes the cache back, unless `[instance] keep_pipeline_cache = 1` (then its saves write a private file of the shared size, 2-6 GB, and the folder gets the marker file `keep_pipeline_cache`) |
| `[nvn] setup_on_start` | `true` | `false`: the "Preparing shaders" window writes the shared shader data. `--prepare-shaders` refuses `--instance` |
| `[album] dir`, `[nvn] shot_dir`, `[test] out`, `[prof] sample_out` | relative to the game folder or exe | inside the instance folder |
| `[test] shot_dir`, `[test] record`, `[diag] soak_csv`, `[prof] trace`, `[time] csv`, `[audio] wav_dump`, `[nvn] dump_missing`, `[nvn] dump_astc` | off unless set | inside the instance folder when set to a relative path |
| Screenshots and texture dumps with relative paths (`[boot] screenshot_at`, `[nvn] trace_frame` PNGs, `gpu_fault_vendor.bin`) | working folder (game folder) | instance folder |

`[instance] keep_pipeline_cache` (default `false`): see `[nvn] pipeline_cache` above. Pipelines an instance builds that the shared cache lacks
come from the driver's own disk cache on its next start. Every instance start also removes the `pipeline_cache.bin` of the other folders beside
its own (the instance root, e.g. `worki_run\oot`) that no running instance holds (their run crashed, was killed, or came from a build that
still wrote private caches), except in folders with the `keep_pipeline_cache` marker; the log line `removed the pipeline caches of N instance
folders` says how much went. Before this, every named instance kept a private copy of the whole cache (150 GB in 50 folders, 2026-11-08).

Shared by every run: the game files (exefs, romfs), the shader cache (`[nvn] shader_cache`; the on-demand translator writes each `.spv` under a
temporary name and moves it into place, and appends `results.tsv` rows under an exclusive-write open), the BC7 cache (`[nvn] bc7_cache`; temporary
name and rename), `game_running.lock` (every run holds it, open for shared writing), and `programs.bin` / `prepare.state` (written only by the
shader preparation).

## Test tooling keys (`[test]`, work area S5)

All off by default; details in `include/nxrt/tt.h` and `docs/S5.md`. Environment variable = `NXRT_TEST_<KEY>`.

| Key | Default | Meaning |
|---|---|---|
| `script` | empty | Scripted run (`.nxs`, grammar in `include/nxrt/tt_script.h`). Exit code 0 pass, 1 fail, 2 usage/parse error, 4 crash, 5 freeze, 6 process ended early, 124 wall timeout. |
| `enabled` | `false` | Turns the test tools on by themselves, without a script, record, replay, deterministic or trace key set. |
| `unplug_player1_at_s` | `0` (off) | Seconds after play mode starts, player 1 reads as disconnected (as when the console's only controller is pulled) until the controller applet answers: reaches a game's own ShowControllerSupport call (`src/gfx/play/play.cpp`, `src/services/am.cpp`). |
| `applet_windows_at_s` | `0` (off) | Seconds after play mode starts, opens the error and network notices and the web page question (example.com) once, with test texts: checks the native applet windows while the game runs. |
| `controller_min_players` | `0` (off) | The controller applet treats the game's minimum player count as at least this (2..8): reaches the controller dialog with a one-player game. |
| `regions` | `regions.tsv` next to the script | Name table for `@area` / `@warp` (`name<TAB>world guid<TAB>area guid`). |
| `out` | `testout` | Output folder: `result.json`, `trace.jsonl`, `shots/`. |
| `deterministic` | `false` | Virtual clock (one frame = `clock_step_ticks`), seeded RNG, fixed wall-clock epoch. |
| `seed` | `0x5EED5EED` | RNG seed of deterministic mode. |
| `clock_step_ticks` | `320000` | Virtual ticks (19.2 MHz) per frame. |
| `frame_source` | `hook` | `hook` (needs a frame entry hook in the game's sites file), `tick` (`diag_frame_tick`), `svc:N` (a frame every N SVCs, bring-up), `manual` (tests). |

| `record` / `replay` | empty | Record the live pad of every frame / feed a recorded input trace. |
