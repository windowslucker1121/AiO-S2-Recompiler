# hwcheck: per-instruction hardware oracle for the Ampere front end

Runs single Ampere ALU and memory instructions on the real GPU and the same instructions through our SASS-to-SPIR-V translation on Vulkan, with the same register inputs, and compares the results bit for bit.

## Run

```powershell
dotnet run --project tools\shaders\hwcheck -c Release
dotnet run --project tools\shaders\hwcheck -c Release -- --only "^FFMA"    # one class (regex on the opcode.modifier key)
```

- Exit 0 means no mismatch. Exit 1 means at least one mismatch, hardware error, decoder disagreement or exception.
- Report: `tools\shaders\build\hwcheck\report.txt`. Per case: `results.tsv` (id, source, key, status, mismatched threads, text, words, example).
- A full run takes a few minutes on an RTX 3080 (about 1400 instructions, 1024 threads each); the first run after the corpus changes also rebuilds the corpus sample cache. The process runs at below-normal priority.
- A case whose GPU launch fails costs a new CUDA worker process (a few seconds each), so many hardware errors make a run slow.

Options:
- `--corpus <dir>`: the nvdisasm oracle of the game's shaders. Default `work/shaders/oracle/SM86`, used only if present.
- `--no-corpus`: use only our own encodings.
- `--per-shape N`: instructions kept per operand shape (default 2).
- `--threads N`: threads per case (default 1024).
- `--seed N`: seed for the input generator.
- `--out <dir>`: output folder.

Needs:
- an NVIDIA sm_86 GPU with its driver (`nvcuda.dll`, `vulkan-1.dll`);
- the CUDA toolkit (`ptxas`, `cuobjdump`, `nvdisasm`), found through `CUDA_PATH` or `PATH`;
- the shaders build prerequisites (`third_party\` staged by `scripts\setup_ryujinx.ps1`). Building this project also builds the harness.

## How it works

1. **Encodings.**
   - `ops.ptx` is our own PTX, about 180 ALU forms, generated by `gen_ops.py`. It is compiled with `ptxas -arch=sm_86` and the words are read back with `cuobjdump -sass`.
   - If the corpus exists, encodings are also sampled from the game's nvdisasm oracle. They are cached in `build/hwcheck/corpus_samples.tsv`; no game file is written to the repo.
2. **Window.** Each instruction is rewritten into a fixed window:
   - registers R0..R15 and predicates P0..P6;
   - constant-bank and uniform-register sources become register sources;
   - a uniform destination is copied into R15.

   The rewritten word must keep its opcode and modifiers, and `nvdisasm` must print the same text as our decoder. Otherwise the case is reported as "decoder-disagrees" or "rewrite changed it".
3. **GPU side (`Cuda.cs`).**
   - `template.ptx` gives the ELF shell.
   - The kernel loads R0..R15 and the predicate word from a buffer (28 words per thread), runs the test instruction, and stores everything back.
   - Before the first run, the kernel text is checked with nvdisasm.
   - Control bits: stall 15. Variable-latency instructions get a write scoreboard, and the next instruction waits on it.
   - The cubin runs through the CUDA driver API in worker processes, because launch errors are sticky.
4. **Our side.**
   - `spirv_harness --hwcheck` wraps the same instruction in a compute shader (`AmpereHwcheck.cs`): load the window, `InstEmit.EmitAmpere`, store.
   - `Vk.cs` runs that shader on the same device with the same input buffer.
5. **Inputs (`Inputs.Make`).** Every warp gets one flavour:
   - fp32 edge values plus random values;
   - fp16 pairs;
   - integers;
   - raw random bits;
   - fp64 pairs;
   - small values.

   The edge values include zeros of both signs, denormals, FLT_MIN/MAX, inf, NaN, ±1 and halfway cases. The predicate word is random.
6. **Memory tests (`Mem.cs`).** Each thread owns a 32-byte window M (words 20..27 of its record, compared bit for bit). The address register is set so the access lands in M's copy:
   - shared (LDS, STS, ATOMS): M is copied to shared byte `thread * 32` before the test and back after it. Each thread touches only its own bytes, so thread order does not matter.
   - local (LDL, STL): M is copied to byte 0x400 of a 2 KB local frame. The GPU side's frame starts at `c[0x0][0x28] - 0x800`, so that side adds the frame base to the address register around the test.
   - global (LDG, STG, ATOMG, RED): the address pair is M's offset in the thread's record. Each side adds its own buffer base just before the test and zeroes the pair after it, unless the instruction wrote it. On our side the base is the storage-buffer descriptor `c[0][0x10]`, so the normal global-to-storage path is tested.
   - Refused: absolute addresses (shared/global: every thread would hit one word; local: the GPU side's frame is not at local address 0), uniform-register address parts (most corpus LDG/STG use `[R.U32+URn]`), scaled local addresses, and address registers that are also data.

## Tolerances

Integers and floats are compared exactly; any NaN equals any NaN. MUFU results come from the driver's GLSL.std.450 functions, so they get a per-function tolerance:

| MUFU form | tolerance |
|---|---|
| RCP, RSQ, SQRT, EX2, LG2 (f32) | 2 ulp |
| SIN, COS (f32) | absolute 2^-20 |
| TANH (f32) | absolute 2^-10 (`tanh.approx` max relative error 2^-11, PTX ISA) |
| any .F16 form | 1 ulp of the f16 result |

HMMA (tensor core) results get an error bound from the warp's inputs, per destination element, with B = sum of the absolute products plus the absolute accumulator: hardware and translation may differ by 2^-9 B (F16 destination) or 2^-15 B (F32) plus one ulp of the result. When B reaches the destination's largest finite value, any result passes (intermediate overflow decides between inf and NaN). An inf or NaN input element requires the same result class. Measured on the RTX 3080 against the exact sum rounded to nearest: HMMA.1688.F16 matched on every element, HMMA.16816.F16 differed by up to 2^-10.0 B, the F32 forms by up to 2^-16.0 B (the tensor core drops low bits of the aligned terms; that summation is not reproduced bit for bit). LDSM and MOVM are compared exactly.

Infinities and NaN must match exactly under every rule. Signed zeros must also match, except where a tolerance applies.

## Coverage

- **Covered:** every ALU class in the corpus, plus the memory classes that need no texture or descriptor:
  - fp32 arithmetic, compares and conversions (FADD, FMUL, FFMA, FMNMX, FSEL, FSET, FSETP, FRND, F2I, I2F, I2FP, F2F, F2FP);
  - fp16 (HADD2, HMUL2, HFMA2, HMNMX2, HSET2, HSETP2);
  - MUFU;
  - fp64 (DADD, DMUL, DFMA, DSETP, 64-bit conversions);
  - integer (IADD3, IMAD, LEA, SHF, LOP3, PLOP3, ISETP, IMNMX, IABS, SEL, SGXT, POPC, FLO, BREV, BMSK, PRMT, MOV, I2I, IDP, VABSDIFF);
  - warp operations (SHFL, VOTE, REDUX, MATCH);
  - tensor cores: HMMA (1688/16816, F16/F32 accumulator), LDSM (M88/MT88, 1/2/4 matrices, shared memory window), MOVM.MT88;
  - memory: LDS, STS, ATOMS, LDL, LDG, STG, ATOMG, RED (see the refused forms above; every corpus STL uses an absolute address).
- **Not covered:** texture, surface, constant, attribute and barrier instructions (they need resources, not just a register file).
- **Window limits:**
  - P2R, R2P and PLOP3 forms that read PR or uniform predicates;
  - IMAD with RZ multiplicands and a uniform-register addend (`IMAD.U32 R37, RZ, RZ, UR9`): the register form of the same word prints as IMAD.MOV, so the rewrite refuses it;
  - HSET2.BF with a constant-bank source: the register form loses .BF;
  - ptxas's own LDG/STG (memory-descriptor form, `desc[UR4]`): our decoder reads the descriptor as an address part. The game corpus does not use this form.

## Cooperative-matrix HMMA (`--coopmat`)

```powershell
dotnet tools\shaders\build\bin\Release\net10.0\hwcheck.dll --coopmat [--out <dir>] [--warps 64] [--header runtime\src\gfx\vk_coopmat_probe_spv.h]
```

Checks the HMMA path of `ampere/frontend/AmpereCoopMat.cs` (one `OpCooperativeMatrixMulAddKHR` per HMMA, matrices built from each
lane's fragment registers) on the local GPU, through Vulkan only (no CUDA toolkit): `CoopMat.cs`.

- Lists the VK_KHR_cooperative_matrix properties and the subgroup size; the path needs 16x8x16 float16 subgroup matrices with float16
  and float32 accumulators and 32-lane subgroups.
- **Element-order probe.** Vulkan leaves the order of an invocation's matrix components to the implementation. HMMA.16816.F16 and .F32
  are translated with the identity order and run on random fp16 inputs; every candidate order (A by register with half swaps, B and
  C/D by element) predicts that run's output from the CPU reference of the PTX fragment layout, and the ones that match within the
  HMMA tolerance are the device's order. None means the device does not give each lane its fragment's elements (the path cannot work).
- Then the translator's own order is checked against the CPU reference and the scalar emulation.
- `--header` writes the F16 module with the translator's order, bit-exact test inputs (small integers) and expected outputs as the
  runtime's start-up probe (`runtime/src/gfx/vk_coopmat_probe.cpp`). Run it again after changing the translator's HMMA path.

Found on an RTX 4080 (driver 610.88, 2026-11-08): component index i holds PTX element `A=0,1,4,5,2,3,6,7` (A registers 1 and 2
swapped), B and C/D in fragment order, for both accumulators; 16 orders match, all equivalent (a consistent swap of k positions in A
and B). The translator's order then agrees with the CPU reference within the HMMA tolerance (F16: up to 160 ulp on near-cancelling
sums, the tensor core's own rounding; F32: bit-identical to the scalar emulation).

- **Packed-half arithmetic.** The variant also computes HADD2 / HMUL2 / HFMA2 with a half result in float16 (one rounding)
  instead of fp32 arithmetic rounded twice and, for HFMA2, an fp64 round-to-odd step. `--coopmat` checks nine forms from OoT's
  network passes against the scalar emulation on hwcheck's input generator (edge values, denormals): bit-identical (HADD2 may differ
  by 1 ulp, the emulation's double rounding; none seen on the RTX 4080).
- `hwcheck --pipeline-stats <a.spv> ...` prints the driver's statistics of compute modules with the network passes' descriptor layout
  (VK_KHR_pipeline_executable_properties: registers, binary size, shared memory) and the pipeline build time.
## Findings (2026-11-04, RTX 3080, driver 617.42)

- **fp32 denormals without .FTZ.** The 3080's Vulkan driver reports `shaderDenormPreserveFloat32 = false` (and `shaderDenormFlushToZeroFloat32 = false`), so DenormPreserve cannot be used. The front end emulates the IEEE result of FADD, FMUL, FFMA, FMNMX, FSETP and FSET without .FTZ: a fast path, and an fp64 slow path when an input is denormal or the result is tiny (`AmpereEmit.Denorm.cs`).
- **Memory ordering in the structurizer.** Ryujinx's AstOptimizer moved a single-use memory load (and an atomic) to its use, past stores in between, and the project's earlier patch then ran a folded atomic twice. Both are fixed in `harness/translator/spirv-call-args.patch`. Found by the LDG and ATOMG cases.
- **IMAD.WIDE's addend must be an even register pair.** An odd pair gives CUDA_ERROR_ILLEGAL_INSTRUCTION. The rewrite keeps it even.

## Known open items

- A full run shows the current state in `report.txt`. Forms the front end still refuses: DFMA with a directed rounding mode, F2FP.SATFINITE, F2FP.MERGE_C with RELU/BF16/directed modes, VABSDIFF with a predicate destination, ATOMS/ATOMG CAS and 64-bit atomics.
- HMMA .BF16 is refused by the front end: a denormal bf16 input becomes an fp32 denormal, which the host flushes (no DenormPreserve) and the tensor core keeps. No corpus uses it. 1684/TF32 and LDSM.M816/M832, MOVM.M832/M864 are decoded but not translated.
- SURED (Mario Kart World) is decoded and translated as an image atomic, but this oracle has no image test, so it is not checked here.
